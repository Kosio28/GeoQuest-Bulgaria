# Global leaderboard

Open `leaderboard.html` through the main navigation. Both languages share the existing language preference. Ranking uses each eligible account's highest individual five-round game, then earliest achievement time, score ID and user ID for deterministic ties. Difficulty and mode filters run before personal-best selection. Pages contain at most 20 players; the top three appear on the podium. Personal ranking is calculated across the entire selected category, independently of the page.

## Existing data and deployment

The implementation reuses Supabase Auth, `game_scores`, pending-score retries, owner-only history and the current distance formula. Live inspection found one compatible historical game, scoring 7,649 points, and no profile table or historical difficulty. That record was preserved. Null difficulty is displayed as Unspecified; it is never guessed from duration. The new minimal `profiles` table stores only public username/avatar fields. Existing accounts can choose a public username in Account. Until then, the UI displays an unnamed-explorer label without deriving a name from email.

`supabase/migrations/20261124184104_global_leaderboard.sql` was applied to the existing project. It adds score eligibility metadata, ranking indexes, `profiles`, and bounded ranking/submission RPCs. No scores were copied, deleted or rewritten. Apply the checked-in migrations in order for a separate environment. Use the existing frontend Supabase URL and publishable key; no new services, Realtime, service-role key or configuration are required for the leaderboard.

The settings migration adds the supported difficulty/time-limit fields without inventing historical values. New submissions receive their scoring version, verification state, achievement time and difficulty's nominal time limit from the database RPC. All-time results include the current `distance-v1` formula and known compatible legacy records with null version. Explicitly different scoring versions are excluded. A future scoring formula must use a new version and its own eligibility category.

## Security and limitations

Direct authenticated inserts into `game_scores` are revoked. Existing owner-only SELECT RLS remains; no UPDATE or DELETE is granted. The submission RPC derives ownership from `auth.uid()`, excludes anonymous Auth accounts, validates points within 0–25,000, bounds duration, validates mode/difficulty, sets server achievement time, and always marks browser submissions unverified. A UUID is assigned once per browser game; the existing `(user_id,id)` primary key makes retries idempotent. Per-player transaction locking ensures simultaneous submissions compare personal bests consistently.

This architecture still receives scores and difficulty from a modifiable browser. A caller can forge an in-range score, fake difficulty/duration, or invent another game UUID. Idempotency prevents duplicate submissions of the same ID, but cannot prove that different IDs represent different played games. Timers, completion, movement restrictions and actual guesses cannot be authoritatively attested by the current game. Do not advertise these results as cheat-proof or competitively verified. Server-verified-only filtering is available, but no browser submission can award itself that status. Secure competitive play needs server-created sessions, authoritative round selection/answers, server timing and server scoring before any score can be marked verified.

Public queries return only rank, public player ID (for own-player highlighting), username/avatar, score, mode, difficulty, achievement date and verification state. Auth emails and raw user metadata are never queried publicly. Both RPCs deliberately use fixed-search-path SECURITY DEFINER functions with explicit role grants: cross-player ranking needs a narrow public projection while raw scores remain private; submissions need controlled writes while direct inserts stay revoked. The private ranking helper is not executable by browser roles. Supabase advisors flag the intentionally callable definer RPCs; this is an intentional API boundary, covered by role tests. The pre-existing leaked-password-protection warning is unrelated and was not changed.

## Verification

`npm test` runs the existing gameplay tests and isolated PGlite Postgres tests using mock Auth roles and fixture accounts that never reach production. Coverage includes best-per-player selection, earliest ties, mode/difficulty filters, scoring compatibility, pagination, historical preservation, off-page personal rank, personal bests/lower results, idempotent submissions, bounds, guest access, anonymous account exclusion, ownership/RLS, and forbidden edits. `npm run build` checks TypeScript and production bundling.

Rendered QA used headless Edge through Playwright because the Browser plugin was unavailable: desktop 1440×1100 and mobile 390×844. Live checks covered the historical score, bilingual headings, filters, empty states, navigation and guest sign-in dialog. Isolated browser API fixtures covered three podium places, pagination, off-page authenticated statistics, own-row highlighting, errors and retries. No fake users or scores were inserted in production. Authenticated production sign-in and a complete live panorama game were not performed in this task; submission and ownership behavior were verified in isolated Postgres instead.
